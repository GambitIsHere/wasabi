01Executive summary

Wasabi replaces VWO with our own experimentation platform — and unlike VWO, it ties every test to real payment P&L. It assigns each visitor a sticky variant, routes them through our existing ?theme= mechanism, and reads the result straight from the payments database: first-payment approval, rebill collection, revenue per customer, and statistical significance.

Why it matters VWO (today) Wasabi (live)
Cost ~€6,000 / yr ~€0 — Vercel + Neon free tiers
Test ↔ revenue Not connected Same database
Data ownership VWO's servers Ours
The verdict Thank-you-page conversion % Auth / rebill / LTV per variant + significance

The ask of the CTO: review this, then own it and approve the company-wide rollout — (1) move the repo into the org, (2) wire the first storefront (Top Up) to prove it on real traffic, (3) roll across the rest and retire VWO.

02What's built & live today

A full create → assign → verdict loop is live in the browser at wasabi.sanjow-hub.com:

  • Experiment dashboard & editor — create/configure experiments (variants, traffic split, ?theme= routing, live validation, activate/pause/delete).
  • Sticky assignment API (/api/decide) — storefronts call one endpoint; PostHog-wire-compatible; the existing theme system is untouched.
  • Live per-variant P&L verdict — acquisition funnel, net revenue, break-even CAC, currency-aware, two-proportion significance test → ship / keep-running / inconclusive call.
  • Test backlog (/backlog) — sourced live from YouTrack (tag: experiment, 41 tickets tagged); one click prefills a new experiment from a ticket.
  • Admin gate — Google SSO (@sanjow.com); storefront APIs stay public.

Deferred (by design): session recording / heatmaps (MS Clarity stays for now); persisted capture events (/api/capture is a compatibility stub). Neither blocks the rollout.

03Architecture

The insight: we already owned most of the pipeline — variant→product resolution (?theme=), attribution (Transaction.themeId), and analysis (Metabase). The only missing piece was assignment, built in-house and PostHog-compatible.

visitor → storefront (Next.js middleware, edge) → POST /api/decide { distinctId } ← SHA-1 hash → [0,1) bucket → variant slug per experiment → redirect/rewrite adds ?theme=<slug> → existing theme-resolver picks the product/billing variant [UNCHANGED] → Application.themeId → Transaction.themeId [UNCHANGED] → Metabase (global-api DB) → verdict: auth / rebill / LTV → two-proportion significance test → ship / keep-running

The one detail worth knowing: assignment is a storage-free, deterministic SHA-1 hash of "{experimentKey}.{distinctId}{salt}" → a number in [0,1). Same inputs → same arm on any machine, no DB lookup. PostHog's SDKs use the same scheme, so we can swap to/from PostHog later without reshuffling users.

05Install from scratch

Vercel-root is dashboard/. The steps below stand up a fresh, production-equivalent instance.

Prerequisites

  • Vercel account/team (current: SVK-OP) + a project with Root Directory = dashboard, Node 24.
  • Neon Postgres database (Vercel's managed Neon integration injects DATABASE_URL automatically).
  • Google Cloud OAuth client (for SSO) — consent screen set to Internal.
  • Optional: Metabase API key (live results) · YouTrack read token (backlog).

Environment variables

VariablePurpose / where
DATABASE_URLreqNeon Postgres (auto-injected by the Vercel↔Neon integration; POSTGRES_URL is a fallback). The experiment store.
AUTH_SECRETreqSession-JWT encryption key. Generate: openssl rand -base64 32. Keep stable.
AUTH_GOOGLE_IDreqGoogle OAuth Client ID (Cloud Console → Credentials).
AUTH_GOOGLE_SECRETreqGoogle OAuth Client Secret. Secret — Vercel env only.
AUTH_ALLOWED_EMAIL_DOMAINreqAllowed sign-in domain, e.g. sanjow.com.
METABASE_URL + METABASE_API_KEYoptLive per-variant P&L results. Without it the results panel degrades gracefully.
YOUTRACK_HOST + YOUTRACK_TOKENoptBacklog source (e.g. sanjow.youtrack.cloud + a read token).
YOUTRACK_BACKLOG_QUERYoptSet to tag: experiment for the clean tag-based backlog (else keyword heuristic).
⚠ Set AUTH_* in EVERY environment
The SSO gate currently fails open if AUTH_SECRET is missing. Production has the AUTH_* vars; ensure Preview does too (Vercel's preview protection covers the gap today, but the gate itself should be made fail-closed — see §06).

Steps

# 1 · clone + deps
git clone https://github.com/GambitIsHere/wasabi.git && cd wasabi/dashboard
npm install

# 2 · Google OAuth (Cloud Console → APIs & Services → Credentials)
#     Authorized redirect URI:
#     https://<your-domain>/api/auth/callback/google

# 3 · generate the session secret
openssl rand -base64 32        # → AUTH_SECRET

# 4 · set env vars in Vercel (Production + Preview), provision Neon
# 5 · Vercel project: Root Directory = dashboard, Node 24, connect `develop`,
#     set Production Branch = develop  (so pushes auto-deploy to prod)

# 6 · deploy
git push origin develop        # → preview;  or:  vercel --prod

# local dev:
cp .env.example .env.local      # fill in values
npm run dev

Verify

curl -X POST https://<domain>/api/decide -d '{"distinctId":"u1"}'   # → 200 (public)
curl -I  https://<domain>/backlog                                  # → 302 → /signin (gated)
# then sign in with an @sanjow.com Google account

06Security & access

SurfaceAccess
/api/decide, /api/capturepublic storefronts call cross-origin
/handover.html, /signin, /api/auth/*public
Everything else (admin UI, /api/flags, /api/tickets, results, /admin/reseed)gated Google SSO, @sanjow.com
  • The gate is an edge proxy (dashboard/middleware.ts) wrapping Auth.js. Unauthenticated → 302 /signin.
  • No secrets are exposed to the client — env vars are server-only.
  • Vercel preview deployments are additionally behind Vercel's own SSO.
⚠ Hardening recommendation
Make the gate fail-closed: if AUTH_SECRET is absent it should deny (500/redirect), not serve. Today a missing secret fails open. Also a minor: middleware.ts → proxy.ts (Next 16 deprecation; cosmetic, still runs).
